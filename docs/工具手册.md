## 日常开发

```bash
make check      # gofmt + vet + build + test，提交前跑这一条就够
make build      # 编译 bin/shiguang 与 bin/sgctl
make test       # 只跑测试
make clean      # 清掉 bin/ 与 dist/
```

跑服务：

```bash
SG_ADMIN_TOKEN=dev-token go run ./cmd/server
# 前台 http://localhost:8080  后台 http://localhost:8080/admin
```

**改了 `web/*.html` 必须重新编译**——两页是 `go:embed` 进二进制的，直接改文件不会生效。

前端没有构建链，但 `go:embed` 也不校验内容，所以内嵌 JS 的语法错误只有运行时才暴露。本地想提前查：

```bash
sed -n '/^<script>$/,/^<\/script>$/p' web/index.html | sed '1d;$d' > /tmp/c.js && node --check /tmp/c.js
```

CI 会自动做这件事（见 [CI](#ci)）。

## 批量导入照片

`sgctl` 是单文件纯 Go 二进制，**放在任何能访问服务的机器上都能跑**，不需要和服务同机。

```bash
make sgctl                 # → bin/sgctl（本机用）
make dist                  # → dist/ 下五个平台的二进制
```

`make dist` 产出：`sgctl-{darwin,linux}-{amd64,arm64}` 与 `sgctl-windows-amd64.exe`。

### 推荐流程

```bash
export SG_SERVER=https://photos.example.com
export SG_ADMIN_TOKEN=你的口令

# 1. 先看会怎么分组，不上传任何东西
sgctl import ~/Photos --dry-run

# 2.（可选）想自己定日期/标题/图注，就生成清单模板改一改
sgctl import ~/Photos --emit-manifest

# 3. 真正导入
sgctl import ~/Photos
```

**先 dry-run 是有意义的**：它会用 `⚠` 标出「日期来自文件修改时间而非 EXIF 拍摄时间」的节点。扫描件、被聊天软件转发过的照片通常没有 EXIF，这类节点的日期多半不是真实拍摄日，值得在导入前调整文件夹结构，或导入后在后台改。

### 分组方式（`--group`）

| 模式 | 行为 | 什么时候用 |
|------|------|-----------|
| `auto`（默认） | 子目录里的按目录名归组，根目录散图按拍摄日期归组 | 照片"部分整理过"——最常见 |
| `folder` | 一律按第一层目录名，根目录散图归入「未分类」 | 已经按事件分好文件夹 |
| `date` | 一律按 EXIF 拍摄日期 | 一堆没整理过的散图 |
| `single` | 全部进一个节点（配 `--title`） | 先囫囵导进去，之后在后台慢慢分 |

**只看第一层目录**：`黄山/第一天/`、`黄山/第二天/精选/` 里的照片全部归入同一个「黄山」节点，不会因为分了子目录就拆开。

**导入前把文件夹名改成你想要的节点名，比导入后再改省事得多**——文件夹名直接变成节点标题。

### 清单文件（可选）

在照片目录里放一个 `shiguang.txt` 就能覆盖自动推导的结果。**没有这个文件时行为完全不变。**

```
# 以 # 开头是注释；删掉某一行 = 该项回到自动推导
date = 2019-10-06
title = 小妹的婚礼
description = 全家去了三亚，海边办的仪式

# 每张照片的图注：文件名 = 图注
DSC1000.jpg = 接亲那天早上
DSC1001.jpg = 海边仪式
```

生效规则只有两条：

- **图注**按文件名匹配清单所在目录内的照片，任何 `--group` 模式下都生效；没写的照片仍用文件名。
- **`date`/`title`/`description`** 只在该目录唯一对应一个节点时生效（`auto`/`folder` 的第一层子目录、`single` 的根目录）。否则会明确提示"未生效"，而不是悄悄套到某个节点上。

`--emit-manifest` 按当前推导结果生成模板，**已存在的清单一律跳过不覆盖**（那是你手写的内容）。

### 其他常用选项

```bash
--concurrency 8      # 并发上传数，默认 4；导几千张可调高
--max-mb 30          # 单张上限，需与服务端 SG_LIMIT_UPLOAD_MB 一致
--timeout 5m         # 单次请求超时
--group single --title "外婆八十大寿"
```

### 中断了怎么办

**直接重跑同一条命令。** 照片按 sha256 内容寻址去重，已导入的会被计入"已存在"跳过，只补没传完的部分；节点按「日期+标题」复用，不会造出重复节点。Ctrl-C 是安全的。

429 限流不会导致丢照片——客户端会按服务端的 `Retry-After` 等待后重试，不消耗错误预算。

### 会被跳过的文件

- 非 jpg/png/webp（**按魔数判定，不信扩展名**：改名的 `.txt` 在扫描阶段就被剔除，不浪费一次上传）
- 超过 `--max-mb`
- `.thumbnails`、`@eaDir`、`$RECYCLE.BIN`、以 `.` 开头的目录——整个跳过

混在目录里的文档、视频静默跳过；「看起来像图片却读不了」的会明确报出来。

## 部署与运维

### local 模式（默认）

```bash
cp .env.example .env       # 至少改 SG_ADMIN_TOKEN
docker compose up -d       # app + litestream
```

照片与数据库都在 `data` 卷：`/data/shiguang.db` + `/data/blobs/`。

### s3 模式

`.env` 里设 `SG_BLOB_DRIVER=s3` 与 `SG_S3_*`，然后：

```bash
docker compose --profile s3 up -d     # 额外拉起 MinIO
docker compose exec minio mc alias set local http://localhost:9000 minioadmin minioadmin
docker compose exec minio mc mb local/shiguang
```

s3 模式下上传走 presign 直传：浏览器/CLI 直接 PUT 到对象存储，不过应用带宽。

### 常看的几条

```bash
docker compose logs -f app                    # 日志（JSON 结构化）
curl -sf http://localhost:8080/healthz        # DB ping + blob 写探测
curl -s http://localhost:8080/api/v1/stats \
  -H "Authorization: Bearer $SG_ADMIN_TOKEN"  # 节点数/照片数/占用字节
```

### 导入几千张时的调参

服务端：

```
SG_LIMIT_UPLOAD_RPM=600     # 默认已是 600，一般不用动
SG_WORKERS=0                # 0 = NumCPU，处理 worker 数
```

客户端：`--concurrency 8`。

上传 handler 只做落盘 + 入队，真正的 CPU 消耗由 worker 池自己限流，所以上传限流不需要卡得很死——卡太死只会阻碍正常导入。

## 备份与恢复

**要备份两样东西**，缺一不可：

### 1. SQLite 主库（元数据）

litestream 已在 compose 里配好，实时复制、秒级 RPO。恢复：

```bash
docker compose stop app
docker compose run --rm litestream restore \
  -config /etc/litestream.yml -o /data/shiguang.db /data/shiguang.db
docker compose start app
```

备份目标在 `litestream.yml` 里配（桶名、endpoint），凭证走 `.env` 的 `BACKUP_S3_AK` / `BACKUP_S3_SK`。

### 2. 照片 blob（不可再生资产）

- **local 模式**：定期同步 `data` 卷的 `blobs/` 目录
  ```bash
  rsync -a --delete <volume>/blobs/ backup-host:/backups/shiguang-blobs/
  ```
- **s3 模式**：开桶版本控制 + 跨区域复制，或 `mc mirror` 到第二个桶

blob 是内容寻址（`orig/ab/cd/<sha256>.<ext>`），备份天然增量、可去重、不会覆盖。

### 恢复演练

**建议每季度做一次**：在干净机器上 restore DB + 同步 blobs → 启动 → 打开前台确认照片完整。孤儿对账 GC 会自动清掉多余对象；缺失的对象会在照片打开时暴露出来。

### 崩溃一致性

上传中途 `docker kill` 不会产生半截数据：

- local 写入走「临时文件 → fsync → rename」，对象要么完整要么不存在
- DB 记录晚于 blob 落盘
- 启动时自动把卡在 processing/pending 的照片重新入队（日志里会有 `recovered stuck photos`）
- 过期上传会话由 reaper 每 5 分钟清理

## CI

`.github/workflows/ci.yml`，在 **PR 与推送 main** 时触发。两个 job：

**`test`**
1. `gofmt` 检查（有未格式化文件直接失败并列出）
2. `go vet`
3. `go build ./...`
4. `go test -race ./...`
5. **内嵌 JS 语法体检** —— `go:embed` 不校验内容，语法错误会被直接打进二进制，这一步用 `node --check` 拦住

**`cross-build`**
- `make dist` 交叉编译 sgctl 五个平台，产物作为 artifact 保留 14 天，可直接从 PR 页面下载

同一分支上新推送会取消仍在跑的旧任务。

本地想跑一遍和 CI 一样的检查：`make check`（`-race` 除外，那条是 `go test -race ./...`）。

## 本地起 MinIO 测 s3 模式

不想用 Docker 时直接下二进制：

```bash
curl -sL -o minio https://dl.min.io/server/minio/release/linux-amd64/minio && chmod +x minio
curl -sL -o mc    https://dl.min.io/client/mc/release/linux-amd64/mc     && chmod +x mc

MINIO_ROOT_USER=minioadmin MINIO_ROOT_PASSWORD=minioadmin \
  ./minio server /tmp/miniodata --address :9000 --console-address :9001 &

./mc alias set local http://localhost:9000 minioadmin minioadmin
./mc mb local/shiguang local/shiguang-test
```

跑 s3 契约测试（**不设这个环境变量时会 skip**）：

```bash
SG_TEST_S3_ENDPOINT=http://localhost:9000 \
SG_TEST_S3_BUCKET=shiguang-test \
SG_TEST_S3_AK=minioadmin SG_TEST_S3_SK=minioadmin \
  go test ./internal/blob/ -run S3
```

以 s3 模式起服务：

```bash
SG_ADMIN_TOKEN=dev-token SG_PUBLIC_READ=true \
SG_BLOB_DRIVER=s3 SG_S3_ENDPOINT=http://localhost:9000 SG_S3_BUCKET=shiguang \
SG_S3_AK=minioadmin SG_S3_SK=minioadmin SG_S3_PATH_STYLE=true \
  go run ./cmd/server
```

看桶里实际存了什么：

```bash
./mc ls --recursive local/shiguang | head
./mc ls --recursive local/shiguang/staging/    # 应该是空的，confirm 后会转正
```

## 接口速查

写接口都要 `Authorization: Bearer $SG_ADMIN_TOKEN`。

```bash
BASE=http://localhost:8080
AUTH="Authorization: Bearer $SG_ADMIN_TOKEN"

# 建节点
curl -s -X POST $BASE/api/v1/nodes -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"date":"2026-05-21","title":"黄山两日","description":"云海来得比预报早"}'

# 上传（local 模式）
curl -s -X POST $BASE/api/v1/nodes/$NODE/photos -H "$AUTH" \
  -F file=@photo.jpg -F caption=云海翻涌

# 时间轴（include_photos=false 只要节点元数据，后台左栏用）
curl -s "$BASE/api/v1/timeline?limit=10"
curl -s "$BASE/api/v1/timeline?limit=50&include_photos=false" -H "$AUTH"
# photo_limit=N 每节点最多带 N 张（photo_count 仍是真实总数），前台首屏用
curl -s "$BASE/api/v1/timeline?limit=10&photo_limit=6"

# 那年今日（往年的同月同日，可用 ?date= 指定"今天"）
curl -s "$BASE/api/v1/on-this-day"
# 地点索引 / 同一地点的其它日子
curl -s "$BASE/api/v1/places"
curl -s "$BASE/api/v1/places/$(python3 -c 'import urllib.parse;print(urllib.parse.quote("外婆家"))')"

# 写相纸背面的手记（≤2000 字）/ 给节点标地点（≤80 字）
curl -s -X PATCH $BASE/api/v1/photos/$PID -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"note":"那天下山下到一半开始下雨。"}'
curl -s -X PATCH $BASE/api/v1/nodes/$NODE -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"place":"外婆家"}'

# 改注 / 移动到其他节点
curl -s -X PATCH $BASE/api/v1/photos/$PID -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"caption":"新图注"}'
curl -s -X PATCH $BASE/api/v1/photos/$PID -H "$AUTH" -H 'Content-Type: application/json' \
  -d "{\"node_id\":\"$OTHER\"}"

# 批量移动 / 批量删除（单次 ≤500 张，逐条汇报结果）
curl -s -X POST $BASE/api/v1/photos/batch -H "$AUTH" -H 'Content-Type: application/json' \
  -d "{\"action\":\"move\",\"photo_ids\":[\"$PID\"],\"node_id\":\"$OTHER\"}"

# 回收站 / 恢复
curl -s $BASE/api/v1/trash -H "$AUTH"
curl -s -X POST $BASE/api/v1/photos/$PID/restore -H "$AUTH"
```

错误码：`VALIDATION_FAILED`(422) `UNAUTHORIZED`(401) `NOT_FOUND`(404)
`CONFLICT_DUPLICATE`(409，body 附已存在的照片) `PAYLOAD_TOO_LARGE`(413)
`UNSUPPORTED_MEDIA`(415) `UPLOAD_SESSION_EXPIRED`(410) `RATE_LIMITED`(429+Retry-After)
`STORAGE_UNAVAILABLE`(503)。

## 出问题时先看这里

| 现象 | 多半是 |
|------|--------|
| 改了 HTML 没生效 | 忘了重新编译——两页是 `go:embed` 进二进制的 |
| 照片显示「曝光失败」 | 看 `fail_reason`；文件损坏/非图片就重传，`pixel bomb` 是超过 `SG_LIMIT_PIXELS_MP` |
| 导入报大量 429 | 服务端 `SG_LIMIT_UPLOAD_RPM` 调高，或客户端降 `--concurrency`。**不会丢照片**，只是慢 |
| 导入后节点日期不对 | 那些照片没有 EXIF，回退到了文件修改时间。dry-run 里带 `⚠` 的就是。用清单文件指定，或导入后在后台改 |
| 照片一直卡在"显影中" | 看日志有没有 `recovered stuck photos`；worker 池崩了会由启动恢复/周期重扫兜底 |
| s3 模式 confirm 报 415 | 文件不是有效图片（回读复检拦下的）。重复 confirm 会稳定返回同一个错误 |
| 前台空白/加载慢 | 检查是否有请求卡住。页面**不加载任何网络字体**，如果看到 fonts.googleapis.com 请求说明代码回退了 |
| 后台登录慢 | 左栏应走 `include_photos=false`。如果拉了全量照片说明按需加载失效了 |

日志是 JSON 结构化的，关键字段：`msg` / `path` / `status` / `dur_ms` / `reqid` / `err`。
按 `reqid` 能把一次请求的全部日志串起来。
